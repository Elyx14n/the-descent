# The Descent — Current Context

## Implemented

- A [single-scene sampling investigation](docs/notes/single-scene-sampling-sources.md#actual-renderer-experiments) found that consistent premultiplied alpha and matching samplers can hold the real player's brightness centroid within about 0.01 native pixels in one scene, but its artwork still softens/sharpens across camera phases. Larger scene textures cost substantially more pixel area. Short offscreen timings established no preparation-time improvement. These are isolated probes; the current interleaved direct-actor renderer remains unchanged, and no shared-target or fading/presentation separation refactor has been implemented.

- The user confirms that iteration 3 seemingly fixes diagonal jitter completely. It retains fractional camera presentation while rasterizing scenery in aligned 321×181 targets, with one pixel of right/top coverage. Static runs draw around directly presented actors to preserve depth without filtering actors twice; lighting dependencies and HUD order stay intact. The normal preview uses `compose_scroll: true`; disabling it restores iteration 2, which fixed camera shake but reintroduced scenery tearing/jitter. A 16-offset renderer probe removed reproduced seam/atlas-bleed pixels and kept the actor centroid fixed. All 192 native tests and RuboCop pass. HD stays off. The user is comparing this solution with deliberately less frequent, discrete movement before settling the final policy. See the [playtest record](docs/notes/decoupled-rendering.md#residual-jitter-playtest-iteration-3).

- Gameplay now uses an application-owned fixed 60 Hz clock with zero or more updates and one lighting/render pass per callback. Previous/current player positions interpolate artwork, camera following, depth, lamp/receiver geometry, and diagnostics together; foreground fading uses fractional presentation time. Pressed gameplay actions queue until consumed once; movement/sneak use the latest held sample. Eight-step catch-up limits and 250 ms stall resynchronization bound work, while reload/respawn/teleport reset interpolation history. Export polling now runs every 500 ms of elapsed time. Offscreen load playback maintained 59.96–60.08 gameplay updates/s at 44.72–59.75 callbacks/s with no discarded time; the previous loop lost gameplay time as callbacks fell behind. Exact native live-session replay is deferred. See [ADR-0016](docs/adr/0016-fixed-step-simulation-and-interpolated-drawing.md) and the [measurements/playtest guide](docs/notes/decoupled-rendering.md). Display motion and interpolation latency still need human playtesting.

- RoomPreview now integrates filled lighting for all enabled room lights and the player. [ADR-0014](docs/adr/0014-use-collider-bases-for-lighting.md) adopts active object colliders as ground-plane blockers, including open/closed door geometry. Mounted artwork shares host bases and source exclusions. Mounted emitter origins sit one world pixel in front of the host baseline, preventing zero-area floor polygons when a colliderless ledge overlaps a separately owned wall; those walls remain blockers. Caps and colliderless objects create no additional casters. Player radius is 64; other lights default to 48 unless authored positive. Sources use ground-plane origins (the player uses its foot-collider center to avoid southern contact collapse), and 32-sided circular boundaries limit visibility. A stateless Lighting module prepares polygons, fills the floor-only lightmap, and samples receiver bases to tint foreground artwork; caps receive ambient. Foreground faces and horizontal doors reject lighting from behind via `front_y`; top-down strips retain base sampling. Receiving visibility uses an inward-side boundary check to prevent vertex-rounding flicker during movement. The floor uses the existing `light_mask.png` alpha for soft radial falloff clipped to sight polygons; foreground base shading remains a linear-distance approximation. The separate LightingPreview was removed. Foreground fading also uses active colliders under [ADR-0015](docs/adr/0015-use-colliders-for-foreground-fading.md); generated alpha geometry and magenta outlines have been removed. See the [frame interface](docs/adr/0005-render-data-and-room-preview.md#render-data-interface) and [learning guide](docs/notes/raycast-lighting.md).

RoomPreview now owns one bounded cache of fixed-room polygons, comparing source data, collider bounds/ownership, and circle/default settings. Doors and source changes invalidate it; successful reloads clear it. Camera movement, fading, and flame animation preserve it; the player lamp recalculates each frame. Local offscreen software-rendered moving-player playback improved from 27–33 FPS without reuse to 59–63 FPS with it across both window sizes and debug states; cold-cache/door-transition spikes remain a separate concern. The raycaster retains 64 temporary direction buckets, prepared numeric records, and final-hit allocation; no algorithm replacement or new dependency was added. Historical [many-light audit](docs/notes/many-light-raycasting-audit.md) figures used visual outlines and larger radii, so they do not describe this integrated workload. Rotational sweep remains excluded; a measured grid experiment is a future option only if needed. The initial pass-order/mask playback measured 59.93–63.93 FPS, but its two mounted floor polygons were still collapsed. With those emitters corrected, two all-source software-rendered runs ranged from 53.30–64.14 FPS with diagnostics off, showing substantial host variance; hardware playtesting remains the performance acceptance check. The lighting integration passed 183 native tests covering cache invalidation, moving corner-sample, face-backlighting, wall-contact, render-pass order, and mounted-light front/far-floor coverage; final playback observations are recorded in the [guide](docs/notes/raycast-lighting.md#wired-learning-checkpoint-2026-10-19). Human playtesting passes.

## Agreed map approach

The current `RoomPreview` is a development aid for discrete room authoring and testing. Its single player, one-room camera bounds, and reload resets are preview assumptions. Tiled resources, the deserializer, Room data/rules, and Render's frame interface remain reusable for the map; see [ADR-0005](docs/adr/0005-render-data-and-room-preview.md#development-preview-and-map-reuse) for the current limits.

The [fixed footprint and approved shortcuts decision](docs/adr/0003-fixed-map-footprint-and-approved-shortcuts.md) is accepted but not implemented. It specifies six initial rooms, standardized footprints and doorway positions, reusable branching passages, and a permanent connected backbone containing a loop. Runs vary compatible room assignments and open two of four or five reserved shortcuts from approved combinations. The Ritual Gate stays at the starting location; other room identities depend on available tileset art.

Tiled is the accepted main room and passage editor; see the [editor decision](docs/adr/0004-tiled-room-authoring.md) and [research](docs/notes/tiled-room-editor.md). The manual authoring implementation has been replaced by a small importer for finite orthogonal JSON exports with embedded tilesets. No backward compatibility with the old recipes is required. The current authoring conventions are described in the [README](README.md#author-and-preview-rooms-in-tiled).

The earlier [research references](docs/notes/room-arrangement-systems.md), including local DragonRuby samples, remain speculative technique references. No external map generator has been adopted.

## Proposed map data boundaries

These are working data boundaries, not an implemented format:

- Keep tile layers, collision, objects, and doorway sockets in templates with local coordinates. Arrangement manifests describe compatible assignments to fixed slots and approved connections.
- Assign ritual-item and clue locations after selecting the arrangement. Validate reachability, sufficient hints, and distribution across routes; keep clue importance independent of a room's artwork.
- Derive walkability, sight lines, and Witness routes from the arrangement and current door states.
- Hand-place the first arrangement. Extend the implemented Tiled room loading with room and passage placement when building that arrangement.

The recommended first map prototype is two rooms connected by one passage, using consistent map coordinates and combining their drawing groups before sorting. It should establish placement, cross-room collision, and room/object identity before expanding to six rooms. This prototype and any multiplayer support remain unimplemented.

## Proposed state models

- **Run:** `at_sealed_gate → exploring → gate_unlocked → gate_opened → run_complete`, with `caught` terminal. Keep required, found, and placed ritual items distinct from revealed clues.
- **Witness:** `patrol → investigate → search → patrol`; a sighting can trigger `pursue`. After losing sight, search from the last confirmed position and consider likely exits or clue-bearing rooms.
- **Memory:** located and timed sounds, confirmed sightings, and visible environmental changes. Keep confirmed locations distinct from inferences; reading an untouched clue need not leave evidence.
- **Player pressure:** lamp state, movement mode, visibility/hiding, and possibly sanity. Sanity's trigger, feedback, and consequence remain unresolved.

## Proposed build order

1. Author the fixed footprint and place the initial six-room configuration; add ritual-item discovery, descriptive hints, and validated item/clue locations.
2. Add located sounds and Witness sight, hearing, pursuit, and search.
3. Add item carrying and pedestal placement, unlock the gate when all four items are placed, and add completion/failure and restart with new item/clue locations.
4. Validate compatible room swaps and approved shortcut combinations within the same footprint after the first loop works. Add sanity only if its playtest-defined consequence earns its place.

## Open questions

- What gameplay consequence makes sanity useful?
- Do environmental sounds suffice, or is a deliberate decoy needed?
- Which hiding places allow escape, and what evidence lets the Witness check them?
- What clue formulations and placement rules keep the puzzle solvable, spread out, and resistant to memorization?
- What carrying limits and item-to-pedestal assignment rules suit the four-item puzzle? Placement order is explicitly unrestricted.
- Which slot layout, template/socket conventions, and approved shortcut combinations make authoring economical and chases readable?
- What audio and visual cues make the Witness's inferences understandable and fair?
